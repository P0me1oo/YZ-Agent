# Elise SS2022 落地补测

日期：2026-10-21。维护者：P0me1oo。实验版本 v2.23.0，未提交、未发布。

本次结果：在同一 VLESS/Reality/Vision → SS2022 AES128 链路中，只把落地从 Go sing-box 换成 Rust Elise。Elise 落地完成相同大载荷多用约 54% CPU，峰值常驻内存少约 79%。没有测出省 CPU 或稳定提速的收益，不据此迁移到 Rust。此结论针对本次固定实现和测试环境，不能推广为语言本身的优劣。

## 链路、来源和验证

```text
独立客户端 sing-box
  → VLESS + Reality + Vision
前置 sing-box（两组相同）
  → SS2022，2022-blake3-aes-128-gcm
落地 sing-box 或 Elise（唯一替换项）
  → 独立进程的 HTTPS 数据目标
```

Elise 没有本链路需要的 SS2022 出站，本次只比较落地，不开发 Rust 前置。HTTPS 目标与落地在同一台单核服务器，但进程及 CPU 统计已拆开。此前五方案报告的落地 CPU 包含 HTTPS 目标，不能与本报告的落地核心单独数据直接比较。

- Elise 固定为 `Grandova/Elise-Backend` 的 `fcdfd429cb0afd3e36a7a46d8e556c82c9288cca`，程序版本 1.0.1。原仓库 main 干净；快照的 348 个跟踪文件与原仓库逐字节一致，仅增加隔离测试入口 `src/bin/elise-ss-perf.rs`，调用原 Shadowsocks 入站、认证、转发及流量回调，不连接面板。Linux 构建源的 349 文件与保留清单一致。
- Rust/Cargo 1.96.0，保留原 Cargo.lock、默认功能和本地 rustls/quinn-proto 副本，`cargo build --locked --offline --release --bin elise-ss-perf --jobs 2` 成功。沿用原发布优化（opt-level 3、thin LTO、codegen-units 1），使用单线程 Tokio 执行器；产物为 Linux x86_64、静态 ELF，SHA-256 `0381a09729310574fb4c1895c50d7aec955709776713f53c6ff8b2373fca9d08`，落地上传后核验一致。
- Go 工具使用实验工作树 `feat/reality-shortid-relay`，基线 `c7d1fed7582578fad82851449c9a77e4d42daaf1` 加已有未提交修改，复用真实 sing-box 包装器。Go 1.27.0、YZ-sing-box v1.15.0，Linux amd64、CGO 关闭、GOAMD64=v1，`vcs.modified=true`；`GOMAXPROCS=1`、Go 内存软上限 192MiB。原有单元、竞态、静态及构建检查已通过，复用未变来源的结果。程序 SHA-256 `5b6412e0c533e2c7dfead6f9dc7406419567967283d92e54074f44f0f6aeceac`，三机核验一致。
- 前置 Ciallo-HK：约 2GB，AMD EPYC 7663；落地及目标 Panstar-HKL：约 1GB，Xeon E5-2696 v4；独立客户端 KZC-HK Lite：约 1GB，QEMU 虚拟 CPU。三台均为单核 x86_64 Debian、BBR，时间同步状态通过。不同主机 CPU 型号不同，各位置 CPU 时间表示本部署的实际占用，不能直接解释为相同硬件上的计算量。
- 本机与 WSL 仅用于构建、文件控制和脱敏结果汇总，性能载荷全部由独立服务器客户端发起。Go/Rust 均通过 1MiB 上传、下载互通检查。

## 载荷和计量

每组单连接上传、下载各 512MiB；四并发上传、下载各合计 512MiB；短连接上传、下载各 128 个 64KiB 请求，合计各 8MiB。关闭连接复用，所有请求新建连接。

交错顺序为 Go/Rust、Rust/Go、Go/Rust，共三轮。每项间隔 1 秒，组间重启前置、落地和目标。36 项正式测试、1596 个请求和新连接全部成功，完整有效载荷为 12.09375GiB，连同互通检查为 12.09765625GiB，不含协议及网络开销。上传只统计服务端确认收到的载荷，下载只统计完整收到的载荷。

每项最长 130 秒，正式窗口最多 30 分钟，进程和临时规则均设自动停止。每个前置、落地及目标进程按明确 PID 每 0.05 秒读取累计 CPU、RSS、主机 CPU 争用及换页计数，并按客户端开始、结束时间插值；客户端使用 wait4 统计逐进程 CPU 和峰值 RSS，包含程序启动。所有载荷均处于监测覆盖区间。短时采样、CPU 计数粒度和跨机时间同步存在边界误差，小数位仅用于汇总。

## CPU 与内存

每轮四项大载荷合计 2GiB。CPU 为三轮累计时间的中位数，单位秒；内存为大载荷期间观察到的峰值常驻内存，单位 MiB。

| 位置 | Go sing-box 落地组 CPU 秒 | Rust Elise 落地组 CPU 秒 | Go 组内存 | Rust 组内存 |
| --- | ---: | ---: | ---: | ---: |
| 前置 | 5.34 | 5.05 | 40.8 | 41.1 |
| 落地核心 | 6.17 | 9.52 | 40.4 | 8.3 |
| HTTPS 目标 | 5.94 | 6.38 | 34.0 | 36.3 |
| 独立客户端 | 10.43 | 10.60 | 42.0 | 42.1 |

Go 落地三轮分别为 6.47、6.17、5.50 秒；Rust 为 9.52、9.58、9.30 秒，三轮方向一致。大载荷落地 CPU 中位数增加 54.3%，内存减少 79.4%。这个差异发生在被替换的落地实现，前置没有改成 Rust，因此不能说 Rust 优化了前置。

四并发时单核 CPU 占用中位数如下，上传/下载分别列出。100% 表示占满一颗核心。

| 位置 | Go 落地组上传 / 下载 | Rust 落地组上传 / 下载 |
| --- | ---: | ---: |
| 前置 | 28.5% / 29.6% | 24.5% / 30.2% |
| 落地核心 | 46.5% / 20.2% | 50.3% / 42.9% |
| HTTPS 目标 | 33.1% / 24.9% | 41.0% / 25.8% |
| 独立客户端 | 48.9% / 62.6% | 43.2% / 63.0% |

在本部署中，Go 落地核心的占用略高于前置，同时落地主机还承担接近一份落地核心开销的 HTTPS 目标；不能把落地主机全部开销算到代理核心。Rust 大载荷落地开销更高，差异在下载方向尤其明显。短请求中 Rust 落地累计 CPU 较少，但不足以抵消大载荷开销，也不能据此概括为所有负载更省 CPU。

## 速度与连接开销

速度为三轮有效载荷速度的中位数，单位 Mbps。

| 落地 | 单连接上传 | 单连接下载 | 四并发上传 | 四并发下载 | 短请求上传 | 短请求下载 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Go sing-box | 857 | 792 | 932 | 899 | 38.7 | 37.3 |
| Rust Elise | 764 | 918 | 830 | 889 | 40.0 | 28.7 |

上传大载荷中，Go 单连接三轮为 827–870Mbps、四并发 909–933Mbps；Rust 分别为 697–787Mbps、795–867Mbps。本次上传 Rust 三轮均较慢。单连接下载 Go 为 768–917Mbps、Rust 为 831–918Mbps，Rust 中位数更高；四并发下载范围明显重叠，不能据此声称总体提速。

短请求建立连接耗时（含 Reality、代理、HTTPS 握手）中位数：Go 上传/下载 8.95/9.06ms，Rust 8.94/9.16ms。完整短请求为 Go 12.15/12.91ms、Rust 12.22/17.84ms。短请求下载 Rust 更慢，而连接建立时间相近。

## 瓶颈与限制

前置没有接近单核上限，下载客户端约占 63%，尚未测得前置最大转发能力。上传时落地核心与 HTTPS 目标竞争同一颗 CPU；落地主机正式项的宿主 CPU 争用中位数约为 Go 4.0%、Rust 3.5%，峰值约 18.6%/15.9%。Go 组期间存在少量主机换页活动，单项最高约 239 页读入、347 页写出；Rust 组最高约 1 页读入，无写出。主机换页来自全机统计，不能归因于测试核心。

这些争用会影响速度，不能把数值当作独立硬件的吞吐上限。相同落地主机上的三轮 CPU 时间差异方向一致，支持“当前 Elise 大载荷 CPU 更高”的结论；没有 CPU 热点剖析，原因尚未定位，不能归因于 Rust 语言。内存优势也对应隔离核心入口，不能当成完整 Elise 节点服务的内存数字。

本次仅覆盖单用户、单路由、TCP、三轮短时测试，不覆盖 UDP、丢包、长距离、高并发、长时间稳定性、面板计费和完整 Agent 集成。没有重新测试 Realm；之前 Realm 是固定 TCP 透传，与本次解密 SS2022 的落地职责不同，不作直接 CPU 对比。
